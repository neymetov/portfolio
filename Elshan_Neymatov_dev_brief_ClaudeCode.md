# Бриф для Claude Code — сборка личного сайта Эльшана Нейматова

Это техническое ТЗ для агента (Claude Code). Смысловой и брендовый контекст — в `Elshan_Neymatov_brand_brief.md` (RU) / `Elshan_Neymatov_brand_brief_EN.md`, это ТЗ на них ссылается, а не дублирует.

## 1. Что собираем

Личный статичный сайт-визитка. Не портфолио с картинками — сайт должен показывать роль и процессы, которые человек ведёт в компании, а работы — доказательство под ними, не главный герой.

## 2. Стек

- **Astro** — статическая сборка. **React** — только точечные интерактивные острова (islands), не вся страница.
- **Хостинг** — Cloudflare Pages.
- **CMS** — Keystatic (git-based, контент как файлы в репозитории).
- **Домен** — ещё не куплен, регистратор TBD (Cloudflare Registrar / Namecheap).

Подробное сравнение вариантов — `Elshan_Neymatov_brand_brief.md`, раздел 8.

## 3. Источники

- **Дизайн (источник истины по вёрстке, цвету, типографике, отступам):** Figma — `https://www.figma.com/design/2Xiz7BP4rAKak3iTteVwlt/Portfolio`, страница `new_website`, фреймы `Home`, `all works`, `Section 1` (шаблон кейса), `blog`. Вёрстка должна визуально соответствовать этим фреймам — это ТЗ визуальный стиль не описывает.

Файл лежит в репозитории рядом с этим брифом; агент берёт значения токенов оттуда, а не подбирает на глаз по скриншотам. Если файла токенов ещё нет на момент старта работы — сообщить об этом и приостановить вёрстку стилей до его появления, не хардкодить цвета/отступы приблизительно.

## 4. Структура сайта / роуты (финальная версия)

Три шаблона: `/` (Home), `/works` (All works), `/work/[slug]` (Work — карточка проекта). Отдельных `/about` и `/illustration` нет: CV входит в hero на Home, иллюстрация — просто ещё одна рубрика на `/works`, рендерится тем же шаблоном `/work/[slug]`.

**`/` — Home**
- Hero: два баннера — баннер с CV и баннер с изображением.
- Skill-section: карточки (иллюстрация/иконка + заголовок + описание), **не кликабельны**.
- Last-works-section: заголовок, кнопка на `/works`, несколько карточек работ — каждая ведёт на свой `/work/[slug]`.
- Footer-section: баннер с заголовком и кнопкой на внешний мессенджер. Общий компонент, переиспользуется на всех страницах.

**`/works` — All works**
- Заголовок страницы.
- Таб из рубрик — при выборе фильтрует показанные работы.
- Главная работа — отдельный вид: на всю ширину, больше информации, чем у обычных карточек.
- Ряд малозначимых работ — сейчас 4, **количество редактируется из админки** (не хардкодить в вёрстке — компонент должен нормально принимать любое N).
- Баннер с двумя работами одновременно — картинка + описание на каждую.
- Footer-section (общий компонент).

**`/work/[slug]` — Work (шаблон проекта)**
- Главное изображение — на всю ширину, больше информации, чем у остальных блоков.
- Галерея — баннеры трёх типов: разбитый на 2 части, разбитый на 4 части, один баннер на всю ширину. Порядок и состав блоков задаётся из админки на уровне конкретного проекта.
- Footer-section (общий компонент).

## 5. Контент-модель (Keystatic collections)

```
SiteFooter (singleton)
  - title: string
  - buttonLabel: string
  - externalUrl: string        // ссылка на мессенджер

SkillCard (array в Home-сингле или отдельная коллекция)
  - icon: image                 // иллюстрация/иконка карточки
  - title: string
  - description: text
  // без ссылки/slug — карточки не кликабельны

CaseStudy ("work")
  - slug: string
  - title: string
  - shortDescription: text      // для карточек и парного баннера на /works
  - categoryTags: string[]      // рубрики для табов на /works (Brand identity, Illustration, Icons...)
  - isFeatured: boolean         // отмечает "главную работу" на /works
  - heroImage: image            // главное изображение на /work/[slug]
  - galleryBlocks: array<{
      type: 'full' | 'split-2' | 'split-4',
      images: image[]           // 1 / 2 / 4 изображения в зависимости от type
    }>
  - processTag: reference<Process>  // опционально, для внутренней связи с "Роль/Процессы" из брифа

Process (справочно, для внутренней логики/тегов, на карточках Skill-section не как ссылка)
  - title: string
  - problem: text
  - action: text

HomeSingleton
  - heroCvBanner: rich text / structured CV content
  - heroImageBanner: image
  - skillCards: reference<SkillCard>[]
  - lastWorksSectionTitle: string
  - lastWorksButtonLabel: string        // "All works"
  - featuredLastWorks: reference<CaseStudy>[]   // ручной выбор для Home, отдельно от /works
```

Ключевое техническое требование: количество карточек в «ряду малозначимых работ» на `/works` и состав `galleryBlocks` на `/work/[slug]` — не фиксированные числа в коде, а результат того, сколько записей/блоков редактор добавил в CMS. Вёрстка (grid/flex) должна корректно работать при любом N, а не только при текущих 4.

## 8. На будущее — блог (не строим сейчас, но учитываем в архитектуре)

Планируется отдельный раздел «блог»: те же баннеры, что на Home, и шаблонная страница лонг-рида на каждый пост (аналог `/work/[slug]`, но для текста, а не проекта). Фрейм `blog` в Figma — черновой набросок этой будущей страницы, не дубликат-артефакт.

Сейчас блог **не проектируем и не добавляем в CMS**. Единственное требование к текущей сборке: hero-баннер и `SiteFooter` реализовать как переиспользуемые компоненты, не завязанные жёстко на логику "work" — чтобы позже добавить третий тип контента (пост) было расширением схемы, а не переделкой вёрстки.

## 8. Жёсткие ограничения

- Никаких лайв-виджетов, счётчиков подписчиков, автообновляемых лент, real-time контента.
- Минимум JS: React только там, где действительно нужна интерактивность (не оборачивать статичные блоки в компоненты без причины).
- Без анимаций ради анимаций, без агрессивных CTA («забронируй сейчас», социальное доказательство в духе «10 000 подписчиков»), без testimonials/client-logo стены.
- Контент собирается статически на этапе сборки; никаких клиентских запросов за основным контентом.
